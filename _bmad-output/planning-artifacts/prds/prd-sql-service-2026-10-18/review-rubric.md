# PRD Quality Review — sql-service (Team SQL Query Library with RAG-Powered NL→SQL)

*Calibration: university course project (ESPRIT), one microservice in a team build, judged by a 15-minute live demo and a technical report, Week 7 delivery. The bar is "can the owner, teammates, and downstream BMad workflows build and demo this without guessing." Enterprise rigor is not expected.*

## Overall verdict
This PRD is better than the stakes require. It has a real thesis (the library and the generator feed each other, and RAG lift is something you can watch happen), decisions are recorded as decisions, scope is fenced honestly, and most FRs have consequences you can test. What could hurt the demo is a small set of gaps: no fallback if OQ-1 finds no Hugging Face model that meets the hard requirements; a latency budget that only holds if the embedding and Qdrant steps take under ~5 s together, which the PRD never states; a Must FR (FR-26) that relies on a Should FR (FR-25); and a few validator and metric details that would mislead whoever writes the stories. None of these is structural, and each is a short fix.

## Decision-readiness — adequate
Decisions are stated as decisions and carry their reasons inline: "(decision: team-library model, no real authentication)" in FR-5, "(decision: aids debugging and the demo)" in FR-17, "(decision: a notice plus length-only logging is enough for this scope)" in §7. §12 separates three questions that are still open from four that are resolved, with dates. The addendum §H records rejected alternatives along with what was given up (execution, auto-save, schema hints). The `[NOTE FOR PM]` in §6 marks a real cross-team tension: commit-service "owns the Qdrant integration." Someone pushing back on "why no auth" or "why not execute" will find their objection answered.

The weak spot is the biggest risk in the project. The LLM feature depends on OQ-1, and nothing says what happens if it fails.

### Findings
- **[high]** No contingency if OQ-1 fails (§6 Hard requirements, §12 OQ-1) — The hard requirements ask for a free tier with no credit card, "under 5 seconds for a short prompt," reachable from Tunisia without a VPN, and "valid PostgreSQL SELECTs." Together these may rule out every model, especially given free serverless cold starts. The PRD has no answer for "what if no model passes." The course requires an LLM feature, so this is the one way the demo can fail outright. *Fix:* add a decision rule under OQ-1 naming which hard requirement gives way first (for example, relax 5 s to 10 s and raise the gateway timeout, or pick a smaller model and accept a lower SM-2). Set a go/no-go date that leaves time to act.
- **[medium]** Page-size overflow behavior left undecided (§4.1 FR-3) — "Larger requests are clamped or rejected with 400." That is two behaviors, and a test can only assert one. *Fix:* pick one (clamping is friendlier for the frontend) and update §5.

## Substance over theater — strong
There is little furniture. Three personas, each tied to a journey that drives FRs: Sami drives generation, copy, and prefilled save; Leila drives the trust metadata; Karim drives the RAG-lift demo. The JTBDs map to features. The "Learn by example" job is thin but is served by FR-29 showing the prompt next to the SQL. NFRs have numbers (p95 < 300 ms, ≤ 12 s, 15 s gateway). The Vision is specific to this product: "a text file cannot do that" is a claim you can test, not a slogan. The novelty claim (RAG over the team's own saved queries instead of schema pasting) is modest and real.

### Findings
- **[medium]** "Defense against corpus poisoning" overclaims (§4.4 Description) — Index maintenance only keeps out queries that are deleted, deprecated, or not read-only. A saved SELECT that is wrong but read-only (bad join, wrong "active customer" definition) is indexed and becomes an Example for everyone. That is the realistic kind of poisoning in a shared library. The only defense is someone noticing and using FR-7 deprecation. *Fix:* reword to "prevents withdrawn or non-read-only queries from becoming Examples." State that semantic correctness relies on human curation (deprecation), and add one line to §8.1.

## Strategic coherence — strong
The thesis is explicit in §1: "Every query a developer saves makes the next generation better for the whole team." UJ-3 dramatizes it and SM-3 measures it. That is the right metric for the thesis, not an activity count. The MVP is a problem-solving scope and the MoSCoW follows the thesis: the validator, RAG retrieval, index sync, and the seed corpus are all Must. The counter-metrics are real, specific, and each names what it counterbalances.

### Findings
- **[medium]** The LIMIT Warning contradicts SM-C3 (§4.2 FR-10 vs §11 SM-C3) — FR-10 warns on "a top-level SELECT without LIMIT." Almost every useful generated query (aggregates such as "orders per region last week") has no LIMIT, so nearly every response would carry this Warning. That is exactly what SM-C3 forbids: "Warnings nobody reads at 11pm are noise." *Fix:* limit the Warning to non-aggregated SELECTs with no WHERE/LIMIT, or drop it. Reconcile it explicitly with SM-C3.
- **[medium]** SM-3 can't be run as specified and is open to leakage (§11 SM-3, §4.3) — "RAG forced off" needs a switch, but no FR or config item provides one, so the measurement has no build owner. Also, the 15-prompt evaluation set is "about the seed schema," and the Seed Corpus already covers the common e-commerce questions. If evaluation prompts paraphrase seed queries, the lift measures retrieval of near-duplicates rather than generalization. *Fix:* add a config flag or request parameter to turn retrieval off (non-production). Require that evaluation prompts not be paraphrases of seed queries, for example by holding some seed queries out.
- **[low]** The library half of the thesis has no metric (§11) — every SM measures the validator or the generator. Nothing checks that UJ-2 works, for example that searching "region orders" finds the seed query and shows the trust metadata. *Fix:* add a simple secondary SM (for example, "5 fixed library searches return the expected Saved Query in the top 3").

## Done-ness clarity — adequate
Most backend FRs are strong. FR-1, FR-5, FR-6, FR-9, FR-17, and FR-19 have precise status codes, error codes, and edge cases. FR-9's "UNION ALL is accepted (regression guard against over-rejection)" is exactly what a story writer needs. The gaps are in the latency arithmetic, a few validator cases, and the frontend FRs.

### Findings
- **[medium]** The latency budget doesn't add up as written (§6 API gateway, §7 Performance, addendum §A) — §6 says 15 s "covers the worst case of embedding + Qdrant + two LLM attempts," and §7 sets 2 × 5 s for the LLM. The embedding call and Qdrant query have no stated timeout ("LLM and embedding calls each have a timeout"). Addendum §A adds that "transport retries are separate." If embedding also gets 5 s, the worst case is over 15 s and the gateway cuts off a request that sql-service would have answered. *Fix:* state the timeouts for embedding (for example 2 s) and Qdrant (for example 1 s) in §7. Forbid transport retries on the LLM path, or count them in the budget.
- **[medium]** The fullwidth-Unicode attack case is muddled (§4.2 FR-11) — "fullwidth-Unicode `ＳＥＬＥＣＴ` that doesn't normalize into a valid statement." FR-9 applies NFKC, which turns fullwidth `ＳＥＬＥＣＴ` into `SELECT`, so a fullwidth SELECT is accepted. Input that "doesn't normalize into a valid statement" is just a parse error, which another case already covers. The real attack (fullwidth `；` or `ＤＲＯＰ` used to hide a stacked statement) isn't named. *Fix:* rewrite it as two cases: "fullwidth `ＳＥＬＥＣＴ 1` normalizes and is accepted" and "fullwidth-disguised `SELECT 1； DROP TABLE orders` normalizes and is rejected as stacked."
- **[medium]** Locking SELECTs aren't covered (§4.2 FR-9) — "every statement node … is a SELECT variant" accepts `SELECT … FOR UPDATE / FOR SHARE`, which take row locks. That is not "read-only" in practice, and the instructor's "how is this different from checking for SELECT?" question could bring it up. *Fix:* reject (or at least warn on) locking clauses, and add the case to the FR-11 suite and SM-1.
- **[low]** Thin FRs with no consequences (FR-12, FR-15, FR-23, FR-24, FR-27–FR-31) — Most can be inferred. FR-27–FR-31 are UI FRs, though, and story creation will lean on them. FR-30's "offers a direct path to manual save" and FR-31's "delete after a confirmation step" are the only testable hints. *Fix:* add one or two checkable consequences per UI FR (for example FR-29: "examples_used entries link to /queries/{id}"; FR-30: "on 503 LLM_UNAVAILABLE a 'Save manually' button opens an empty create form").
- **[low]** Retrieval count vs threshold (§4.3 FR-14 vs addendum §C) — "retrieves the top 3–5" conflicts with discarding Examples below the threshold. The addendum says 1 passing Example is enough to skip the no-similar Warning, so 1–2 Examples is a valid outcome the FR doesn't allow for. *Fix:* "retrieve up to 5 above threshold; 0 triggers FR-15."
- **[low]** Unbounded "later" (FR-21 "retries the bootstrap later," FR-25 "reconciles later") — neither can be tested. *Fix:* give an interval or a trigger (for example "on next startup and via POST /admin/reindex").

## Scope honesty — strong
Omissions are explicit. §9 Non-Goals does real work (no execution, no introspection, no multi-turn). §2.2 names non-users. The Won't row in §10 is concrete. §8.1 says plainly "sql-service is not a security control." Twelve inline `[ASSUMPTION]` tags are all indexed. Open items are three OQs, about a dozen assumptions, and two `[NOTE FOR PM]`. That density is fine for a course project. The §10 NOTE about shipping the copy button without usage recording is honest de-scoping.

### Findings
- **[medium]** A Must FR depends on a Should FR (§4.5 FR-26 vs §10) — FR-26 (Must) says "indexing completes through reconciliation (FR-25)," but FR-25 is Should. The same applies to FR-1's "indexed flag is then false." Without FR-25, a query saved during a Qdrant blip is never indexed. Someone sequencing stories by MoSCoW will build seeding without the mechanism its consequence relies on. *Fix:* promote the startup half of FR-25 (reconcile on boot) to Must and keep the on-demand endpoint as Should, or drop the reconciliation clause from FR-26.
- **[low]** Must backend with no Must UI (§10) — FR-6 and FR-7 (delete, deprecate) are Must, but their only UI is FR-31 (Should). That's fine if intended (the API is exercised via Swagger), but it isn't said. *Fix:* one line in §10 noting that deprecate/delete may be demoed via OpenAPI if FR-31 slips.
- **[low]** The admin reindex endpoint is open to everyone (§5 `POST /api/sql/admin/reindex`) — this is consistent with the no-auth decision but isn't acknowledged. *Fix:* add it to the Won't row or a one-line note ("unprotected in v1, demo only").

## Downstream usability — adequate
The Glossary is good and mostly followed: Saved Query, Indexed Query, Example, Warning, and Safety Note are used consistently across FRs and SMs. FR/UJ/SM IDs are contiguous, and the FR→UJ "Realizes" links resolve. §5 gives architecture a ready contract table and error taxonomy. One cross-reference is broken, and it matters to the architecture and story workflows.

### Findings
- **[medium]** Broken promise of exact shapes (§5 "Exact shapes are in `addendum.md`") — the addendum has no request/response schemas. Story writers will have to invent the bodies of the create-with-Warning response (FR-1), the deprecation request (FR-7), the validate response (FR-12), and the reindex response. Field names are partly given in FR-18 only. *Fix:* add an addendum section with JSON examples for each endpoint, or change the sentence to say the shapes will be defined in architecture.
- **[low]** "Seed schema" is used but defined only in the addendum (§11 SM-2/SM-3, §4.5) — the SMs require running SQL "against the seed schema in PostgreSQL," but the PRD names only four entities. The DDL is sketched in addendum §E, and no FR or SM gives anyone ownership of creating the evaluation database. *Fix:* add "Seed Schema" to the Glossary pointing to addendum §E, and note that the evaluation harness (addendum §F) owns it.

## Shape fit — strong
The shape is right: a capability spec for one microservice, with an API contract (needed because the gateway, frontend, and commit-service owners integrate against it), plus three named journeys because there is a real UI and a demo audience. UJ-3 is a demo script dressed as a user journey, but that suits the stakes: the demo is the acceptance test. The level of formality matches a chain-top PRD feeding architecture and stories without being heavier than a course project needs.

- **Glossary gaps:** "use" / use_count (FR-8) and "Seed Schema" (§11) are used as terms but not defined. UJ-1 says "team queries" where the Glossary term is Saved Query or Example.
